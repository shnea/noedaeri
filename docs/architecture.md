# 실행 구조와 작업 계약

뇌대리의 기본 단위는 파일이 아닌 작업이다. 공통 큐는 `kind`, `service`, `title`, `input`, `options`, 상태와 결과를 보관한다. 서비스별 입력 검증과 결과 파일 형식은 `services.py`, 실행 코드는 각 워커가 책임진다. 텍스트 입력과 JSON 결과를 쓰는 테스트 서비스도 같은 등록·점유·완료 경로로 검증한다. 이 테스트 서비스는 운영 목록에 등록하지 않는다.

## 초기 구현 범위

FastAPI가 인증·승인·작업 등록·조회·임시 저장을 담당한다. PostgreSQL이 작업과 사용자·세션을 영속 저장한다. FFmpeg 워커는 독립 프로세스로 실행되며 HTTP API로 작업을 가져온다. API와 워커는 현재 같은 호스트의 저장 루트를 공유한다. 원격 PC 워커의 입력 전송은 아직 구현하지 않았다.

웹은 실제 등록된 서비스만 보여준다. 현재 서비스는 `image.package`, `video.thumbnail`, `video.package`다. TTS·임베딩·STT·n8n 워크플로 실행은 이후 추가한다. 입력 타입과 옵션은 작업 유형에 종속되며 향후 서비스 추가 시 전용 입력 폼도 추가한다.

Raya는 작업 큐와 분리한 동기 텍스트 라우터다. 별도 Python 3.12 환경의 공식 ONNX CPU 모델을 요청 시 프로세스로 실행하고 유휴 시 종료한다. API는 전용 추론 키와 승인 사용자 세션을 구분하며 관리자는 상태·시간 정책·메모리 해제·추론 테스트를 제공받는다. n8n의 8개 작업 분기는 실제 Raya 판단 뒤 3개 성능 등급으로 연결한다. 실제 AI 공급자 호출·학습 데이터 수집·파인튜닝은 아직 구현하지 않았다. [Raya 계약](SERVICE_INTEGRATION.md#raya-난이도-판단-api)을 따른다.

## 작업 수명주기

| 단계 | 동작 |
|---|---|
| 등록 | `POST /api/jobs`: 작업 종류·제목·입력·옵션·UUID 멱등 키. 동일 요청은 기존 작업 반환, 다른 내용의 키 재사용은 409. |
| 입력 | 파일 작업만 `PUT /api/jobs/{id}/input`에 원시 바이트 전송. 파일명은 경로에 사용하지 않는다. 파일 없는 입력은 등록 즉시 큐에 들어간다. |
| 점유 | 지원 종류를 선언한 워커가 PostgreSQL `SKIP LOCKED`로 한 작업을 점유한다. 점유 토큰과 만료 시각을 발급한다. |
| 실행 | 주기적으로 점유를 갱신한다. 취소·통신 오류·점유 상실 시 FFmpeg 프로세스 그룹을 종료하고 reap한다. |
| 완료 | 현재 유효한 점유 토큰으로만 보고를 허용한다. 결과 확인 후 완료로 전환한다. |
| 점유 만료 | `interrupted`로 표시한다. 기존 프로세스가 죽었다고 추정하여 자동 재실행하지 않는다. 실행 잠금이 해제된 작업만 failed로 복구한다. 잠금 미적용 구버전 작업은 자동 복구하지 않는다. |
| 정리 | 터미널 작업의 입력·중간 파일을 정리하고 결과는 24시간 후 삭제한다. 실패하면 정리 상태를 남기고 재시도한다. 작업 이력은 유지한다. |

실패·취소 작업은 원본 재업로드와 새 작업 ID로 재시도한다. retry_of로 이전 이력을 연결한다. 워커와 자식 프로세스가 같은 파일 잠금을 상속하며, 점유 상실 후 잠금 해제 확인 전에는 복구·정리하지 않는다. tmp/locks의 작은 잠금 파일은 inode 교체로 잠금을 우회하지 않도록 유지한다. 여러 호스트·NAS 공유 잠금은 미검증이다.

## 인증 경계

웹: 플랫폼 OIDC Code + PKCE S256, state·nonce·서명·issuer·audience·만료 검증. 토큰 원문은 DB에 저장하지 않고 난수 세션의 SHA-256만 저장한다. Secure·HttpOnly·SameSite 쿠키와 변경 요청 Origin·CSRF 검증을 적용한다. 초기 버전은 RS256 서명만 허용한다.

최초 관리자: 암호화 설정의 issuer·subject 정확 일치. 미설정이면 모든 신규 로그인은 승인 대기다. 이후 관리자가 승인·거부·철회한다. 웹 사용자는 자신의 작업과 결과만 조회한다. 관리자에게는 사용자·워커 관리가 추가된다. 전체 사용자 작업 통합 조회는 후속 범위다.

워커: 별도 WORKER_API_KEY로 내부 API를 인증한다. 브라우저에 전달하지 않는다. nginx에서는 `/internal/`을 공개하지 않는다. 외부 서비스별 키·권한·할당량은 아직 구현하지 않았다.

외부 AI·n8n 요청은 플랫폼에서 접수해 뇌대리로 전달하며 기존 파일서비스 플랫폼 키와 `X-Noedaeri-API-Key`를 재사용한다. 현재 `/api/v1/ai/raya/route`는 플랫폼의 동기 난이도 판단을 제공한다. 플랫폼의 n8n 작업 접수·실행은 후속 범위다. n8n 실행 중 Raya를 호출하는 전용 헤더 키는 암호화 설정과 n8n Credentials에 보관하며 외부 앱에 배포하지 않는다. n8n 관리자 API 키나 웹 로그인 자격증명과 혼용하지 않는다. 수동 초안의 8개 작업에서 실제 Raya 호출과 3등급 분기를 검증했다. 실제 AI 공급자 호출과 기존 운영 작업 전환은 후속 범위다. 공통 AI 사용량은 뇌대리에서 관리하도록 연결 설계를 정리했으며 수집·저장·조회 API는 아직 없다. [기존 흐름·usage 연결 기준](SERVICE_INTEGRATION.md#기존-ai-흐름을-연결하는-기준)을 따른다.

## 알려진 운영 제한

- 초기 스키마 생성 방식이며, 운영 DB 업그레이드를 위한 버전별 마이그레이션은 후속 작업이다.
- GPU/메모리 총량 예약은 아직 없다. Raya의 CPU 모델은 요청 시 로딩·유휴 시 해제하며 실제 여유 메모리를 확인한다. FFmpeg는 CPU 또는 macOS VideoToolbox H.264 인코딩을 선택하며 워커당 한 작업을 실행한다. 같은 저장 루트의 하드웨어 인코딩은 파일 잠금으로 하나씩 배정한다. 다른 앱의 하드웨어 사용량과 통합 메모리 여유를 예약하는 전역 자원 관리자는 아직 없다.
- 업로드 기본 5GiB (5,368,709,120바이트), 영상 1시간·4096px·850만 픽셀 이내, MP4/MOV 및 Matroska/WebM 컨테이너를 허용한다. 썸네일은 최대 480×320 JPEG다.
- 원본 전송 재개는 아직 없으며 전송 실패 시 같은 작업의 입력을 다시 보낼 수 있다. 끊긴 입력 대기는 30분 후 실패로 정리한다.
- 저장량 제한은 보수적인 예약과 디스크 여유 검사로 적용한다. NAS 마운트 장애·여러 호스트 간 공유 파일 잠금 검증은 아직 없다.
- 플랫폼 OIDC discovery와 읽기 전용 integration context는 HTTP 200 및 설정 일치를 확인했다. 이는 로그인 성공을 의미하지 않는다. 외부 HTTPS 프록시의 화면·health 응답, 비로그인 작업 조회 차단과 내부 워커 경로 차단을 확인했다. 실제 로그인과 승인한 계정의 운영 접속은 아직 검증하지 않았다.
- 로그아웃은 뇌대리 세션을 즉시 폐기하고 Discovery의 `end_session_endpoint`로 브라우저를 이동해 플랫폼 로그아웃을 진행한다. 토큰 원문을 보관하지 않으므로 `client_id`와 동일 origin 홈 복귀 주소를 사용하며, 플랫폼에서 종료 확인을 요구할 수 있다. 플랫폼 조회 실패 시 로컬 로그아웃은 완료하고 SSO가 유지될 수 있음을 알린다. 실제 사용자 브라우저에서의 SSO 종료는 최종 확인이 필요하다.

## 통합 영상 처리

`video.package`는 같은 업로드 계약으로 썸네일·해상도별 HLS·전체 ZIP을 만든다. 입력보다 큰 해상도는 생성하지 않는다. 480p보다 작은 영상은 원본 짧은 변의 짝수 크기를 사용한다. 비정사각 픽셀과 회전 정보를 반영하고 최대 출력 변은 4096px로 제한한다.

H.264/AAC, 30fps, 6초 단위 MPEG-TS VOD 구성이다. 해상도별 변환은 순차 실행하며 기본 전체 제한시간은 30분이다. `thumbnail`, `encoding_<해상도>p`, `packaging` 단계가 점유 갱신과 함께 기록된다. 실패·취소 시 마지막 단계를 남기며 중간 결과는 공개하지 않는다. 부분 재개는 아직 지원하지 않는다.

기본 `FFMPEG_VIDEO_ENCODER=auto`는 macOS에서 VideoToolbox 디코딩·H.264 인코딩을 시도하며 다른 OS는 CPU를 사용한다. `libx264`는 CPU 고정, `h264_videotoolbox`는 하드웨어 전용이다. 스케일링·썸네일은 CPU를 유지한다. VideoToolbox 인코더는 `-allow_sw 0`으로 실제 하드웨어만 허용한다. 기본 자동 모드에서 `hardware_encoding_failed`가 발생하면 자식 회수·슬롯 반환 후 미완성 해상도별 파일과 manifest 목록을 정리하고 CPU로 전체 해상도를 한 번 재변환한다. 취소·시간 초과·용량 부족은 재시도하지 않고 기존 제한시간을 유지한다. CPU 재시도 실패도 종료한다. 결과 manifest에 실제 `video_encoder`와 `hardware_fallback`을 기록한다.

하드웨어 잠금은 FFmpeg 자식에도 상속하므로 워커가 비정상 종료돼도 실제 변환 종료 전 슬롯을 재배정하지 않는다. 대기 중 `waiting_hardware_encoder`, 자동 CPU 전환 시 `cpu_fallback`을 표시하고 점유 갱신·취소·전체 제한시간을 적용한다. 해상도별 변환이 모두 끝나고 자식이 회수된 뒤 슬롯을 반환하며 ZIP 생성은 슬롯 밖에서 진행한다. 여러 호스트·NAS 잠금과 다른 앱의 예약은 지원 범위 밖이다.

결과 JSON은 `type=video_package`, `master`, `thumbnail`, `download`, `variants`, `files`를 제공한다. 파일명은 상대 이름만 사용한다. `GET /api/jobs/{id}/files/{filename}`은 매 요청 로그인·현재 승인·소유권·만료·파일 목록을 확인한다. `/result`는 전체 ZIP을 반환한다. 모든 결과는 웹 테스트의 24시간 보존 정책을 따른다.

웹은 HLS 지원 브라우저에서 자동·수동 화질을 제공한다. 브라우저 네이티브 HLS 사용 시 수동 변경은 재생 주소를 전환하고 재생 위치를 복구한다. 플레이어가 없는 브라우저는 다운로드 안내를 표시한다. 외부 파일 서비스 등록 API와 서비스별 호출 키는 별도 후속 작업이다.

## 이미지 처리 프로세스

이미지는 FFmpeg와 별개인 Pillow 12.3.0 + pillow-heif 1.8.0 프로세스로 처리한다. 고정된 Python 실행 파일과 인자를 사용하며 키·DB 환경을 상속하지 않는다. 관리 워커의 heartbeat는 계속 유지하고 취소·점유 상실 시 자식 프로세스 그룹을 종료한다. CPU·출력 파일 크기·벽시계 제한, 디코딩 전 바이트·화소·변 길이 제한을 함께 적용한다. OS 메모리 격리나 모든 악성 코덱 입력에 대한 보호를 보장하는 샌드박스는 아니다.

ICC 색상 변환 뒤 EXIF·ICC 등 원본 부가정보를 제거한다. 원본의 실제 형식과 명시한 확장자를 대조하고 JPG·HEIF 같은 동의 확장자를 허용한다. 원본 파일명·원본 파일을 결과에 복제하지 않는다. 이미지마다 출력 2MB를 넘으면 실패 처리한다. 깨진 형식·프로필 등 디코더 오류는 민감한 진단 없이 unsupported_media로 보고한다.

참고 구현 계약: [Pillow 이미지 포맷](https://pillow.readthedocs.io/en/stable/handbook/image-file-formats.html), [pillow-heif 플러그인](https://pillow-heif.readthedocs.io/en/stable/pillow-plugin.html). 실제 지원 여부는 설치된 코덱에 대한 프로젝트 테스트 결과를 따른다.

영상 길이·화질별 목표 비트레이트로 ZIP 포함 출력 공간을 예약한다. DB advisory lock으로 예약 경쟁을 직렬화하고 점유 토큰을 검증한다. 실행 중 실제 출력량을 검사하며 예약 초과는 실패 처리한다. 스키마 변경은 시작 시 반복 가능한 ADD COLUMN IF NOT EXISTS로 적용한다.


## 플랫폼 연결

`/api/v1/`은 전용 헤더 키로 고정 서비스 주체에 연결하며 웹 사용자 세션과 분리한다. 관리자만 웹에서 플랫폼 작업을 조회·취소하고 알림을 재전송할 수 있다. 서비스 주체는 사용자 승인 목록에서 제외한다. 기존 `PLATFORM_API_KEY`·워커 키와 다른 전용 키와 HMAC 공유 비밀을 암호화 env로 관리한다.

종료 작업을 durable deliveries 테이블에 고정 이벤트 ID·불변 JSON 본문으로 수집한다. 정리 전 수집하며, receipt가 먼저 와도 해당 이벤트를 보존한다. 별도 비동기 루프에서 행 잠금으로 한 전달자를 선택하고 HTTPS 서명 요청을 보낸다. 수신 성공과 로컬 커밋 사이의 장애는 중복 전송을 만들 수 있어 수신 inbox의 event ID UNIQUE 처리가 필수다. 조회·접수는 웹훅 전송을 기다리지 않는다. 실패는 최대 8회 후 중지하며 관리자 수동 재전송은 동일 이벤트다.

플랫폼 결과는 기본 7일 보관 상한 또는 저장 확인까지 유지한다. receipt는 해당 job의 terminal_event_id를 검증하며 다운로드를 즉시 닫고 정리를 예약한다. 파일 정리 실패는 기존 cleanup 상태로 표시한다. 입력·중간 파일은 종료 후 정리하며 원본은 플랫폼이 보관한다. 실제 수신 URL 미설정 시 신규 플랫폼 접수를 거절한다.
